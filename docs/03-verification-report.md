40개 명반 × 12개 대한: 대한 칸이 명궁이 되고 이름이 그 칸에서 역행으로 이어진다. 유년은 그 해 지지 칸이 명궁이고 사화는 그 해 천간 기준. 유월·유일·유시도 12궁 이름과 운 사화 4개를 만든다. **유년~유시의 정확도는 U-02 로 미확인 — 엔진 값 그대로**이며 합격은 “구조가 맞음”까지다.

### V-09 역산 (F-09, I-10) — 합격
임의 출생 조합에서 일부 값만 줘도 정답이 후보에 반드시 포함(500건), 값을 모두 주면 후보 하나, 모순 입력은 후보 0건 + 원인 쌍 설명(셋이 얽힌 모순은 “하나를 빼면 가능한 항목”), 후보로 실제 명반을 만들면 입력한 위치와 일치, 13개 값 분석 1초 이내.

### V-10·V-11 해설 반응성·다양성 (I-12, I-14) — 합격 · I-13(길이 균일)은 사용자 결정으로 폐지

- **한계**: 사이트 원본이 시계 시각을 그대로 쓰는지는 확인하지 못했다(기본 결과가 사이트와 달라질 수 있음 — 설계서 C-4).

### V-28 비교 판정과 시기 짝짓기 (T-04·T-05, 신규) — 합격

**검증 수단 자체의 결함**도 있었다. E2E 의 “서버가 받은 주소” 감시 장치가 처음에는 Vite 가 `req.url` 을 `/index.html` 로 바꾼 뒤에 기록해서 **항상 통과**했다 — 예전 쿼리 링크가 서버에 보이는지 같이 확인하는 점검(§6)이 이를 드러냈고, `prependListener` 로 고쳤다. 그 밖에 테스트 가정이 틀린 경우(1990년 윤5월 가정, 水二局에서 d일과 d+24일이 같은 명반이라는 점, 윤달 전반부는 평달과 같은 명반이라는 점 등)는 제품이 아니라 테스트를 바로잡았다.

쉬운 해설 개선에서도 **검사 도구의 결함**이 나왔다. ① 전문용어 목록이 일반 낱말과 섞여 오탐(‘소한’ ← 사소한, ‘화기’ ← 소화기, ‘충’ ← 충돌, ‘대한’ ← “선하게 대한”) → 낱말 경계로 잡는 목록과 부분 일치 목록으로 분리. ② 전수 검사가 157초 걸려 CI 에 부담 → 같은 문장 캐시와 의미 없는 반복 제거로 6초. ③ 샘플 문서의 서식 검사가 빈 줄·들여쓰기를 이중 공백으로 셈 → 줄 단위 검사. ④ 독자 시험의 설계 한계 — 독자 2 가 서로 다른 사람의 명반을 한 사람의 것으로 보고 “연간이 다르다”고 지적했다(해설의 오류가 아니라 시험 안내 부족).

통변 검증에서도 **검증 수단의 결함**이 나왔다. ① E2E 선택자 `details.tb-theory summary` 가 요소 11개와 맞아 strict mode 위반이 났고 그 뒤 흐름(접근성 검사 포함)이 통째로 중단되어 건수가 줄었다 → 선택자를 고치고 모든 흐름이 끝까지 도는지를 건수로 확인한다. ② 변이 검사 스크립트의 “바꿀 곳”이 리팩터링으로 낡아 4종이 ‘건너뜀’으로 나왔다 → 새로 쓰고, 패턴이 맞지 않으면 실패로 보고하게 했다. ③ 단위 테스트 목록 생성기가 건너뛴 생성기 테스트를 ‘✗’로 적어 실패처럼 보였다 → ‘↷ 건너뜀’으로 구분한다. ④ 독자 시험 3차의 에이전트가 API 사용 한도(429)로 한 번 실패했다 → 한도가 풀린 뒤 같은 입력으로 새 독자에게 다시 맡겼다. ⑤ 독자 시험의 사실 문항 채점을 기계 규칙(`score.mjs`)으로 통일했다. “같은 단계의 영역은 집합이 같아야 맞다”는 엄격한 규칙에서는 1차가 35/39 였다 — 한 줄 요약이 같은 단계 영역을 하나만 말한 것이 원인이어서 요약을 고쳤다. ⑥ **푸시한 뒤 CI 를 확인하지 않았다**: 한국식 시각 커밋(`7657831`)의 GitHub Actions(run #8)가 E2E 시간 검사 한 건(“명반 재계산·재렌더 1초 이내”, CI 에서 1,269ms)으로 **실패**했는데, 통변 커밋을 푸시한 뒤에야 알았다. 같은 검사는 통변 커밋(run #9)에서 통과했고 로컬 실측은 120~175ms 이다. 첫 클릭의 준비 비용이 겹친 느린 실행기의 일시적 흔들림으로 보고, 기능이 느려졌는지(회귀)를 보려는 검사이므로 ‘명반 보기’를 세 번 눌러 가장 빠른 값으로 보게 고쳤다(`3e65514`). 원인을 더 파지는 않았다. 재발 방지로 설계 체크리스트에 “푸시한 뒤 CI 결과까지 확인하는가”를 넣었다(05-feedback.md §5).

## 7. 성능과 크기

- 명반 + 사주 + 비교 데이터 계산(`computeOutcome`, 무작위 150건, 로컬 컨테이너): 한국 기준 평균 46ms(p95 61ms, 최대 183ms), 중국 기준 평균 48ms(p95 66ms). 운 뷰 2개(대한+유년) 평균 40~46ms. 궁 해설 12개 평균 1.1ms(p95 2.0ms, 최대 7.5ms — 한눈에 보기가 더해져 0.8ms 에서 늘었음). 역산(3개 값) 1.4ms. E2E 에서 “명반 보기” 클릭부터 화면 갱신까지 1초 이내.
- **통변**(명반 + 사주 + 통변 + 비교, 대한 계산 포함) 한 번에 **평균 140~275ms**(실행마다 140 · 170 · 225 · 275ms 로 달랐음, 로컬 컨테이너, 시험의 한계는 1초). 실제 브라우저에서 “명반 보기” 클릭부터 화면이 다시 그려질 때까지는 로컬에서 120~175ms(종합 통변 탭이 열린 상태, 8회 측정). 첫 화면에서 종합 통변이 3초 안에 나온다는 E2E 검사를 통과한다.
- **느린 실행기에서는 시간 기준 검사가 흔들린다**: GitHub Actions 의 직전 커밋(`7657831`) 실행에서 E2E 의 “명반 재계산·재렌더 1초 이내”가 1,269ms 로 실패했다(통변이 들어오기 전 코드). 로컬 값은 이보다 10배 가까이 낮다 — 실행기 성능과 첫 클릭의 준비 비용 때문으로 보이며 원인은 더 파지 않았다. 통변 커밋의 CI(run #9)에서는 같은 검사가 통과했고, 검사를 세 번 중 가장 빠른 값으로 바꿨다(§5).
- 배포물: `dist/index.html` + JS 한 파일 **1.36MB(gzip 438KB)** — 통변 엔진과 문안이 더해져 1.2MB(gzip 398KB)에서 늘었다. 대부분이 iztro·lunar 계열 라이브러리다. 한국 음력 표는 2.6KB.

## 9. 검증하지 못한 것과 한계

1. **원본 사이트와의 직접 대조는 하지 못했다.** 비교 근거는 원장의 관찰 기록과 독립 구현뿐이다. 사이트의 음력 기준(한국/중국)·득/리 매핑·역산 동작 등이 이에 해당한다. 사용자가 사이트에서 몇 건을 대조해 주면 가장 값싸게 닫을 수 있다(05-feedback.md).
2. **한국천문연구원 원자료를 직접 열람하지 못했다.** 그 자료에서 만들어진 공개 라이브러리(범위 ~2050-12-31)와 대조했다. 2051~2100년은 같은 규칙의 계산값이고, 1912년 이전은 중국 음력과 같다는 표의 사실을 따랐다.
3. **브라우저는 Chromium 계열(로컬 + GitHub 의 Chrome)만** 확인했다. Firefox·Safari 는 미확인. 모바일은 390px 에뮬레이션이며 실기기는 아니다.
4. **음성 읽기**는 재생이 시작되거나 불가 안내가 뜨는 것까지만 확인했다(헤드리스 환경에 음성 엔진이 없음).
5. **해설 문장의 명리적 타당성**은 자동 검사 대상이 아니다. 문장 길이·전문용어 표시·되풀이·구조·반응성만 검사한다. 전통 이론에 따른 서술이며 통계로 검증된 것이 아니다(화면에도 그렇게 표기). 전문가 감수는 하지 않았다. **쉬운 말로 바꾸는 과정에서 전통 해석의 뜻이 달라지지 않았는지도 전문가가 확인하지 못했다**(문안은 개발자가 새로 쓴 것).
6. **유년~유시 운의 정확도(U-02)** 는 엔진 값 그대로이고, 운의 경계(입춘 등)는 날짜 단위다.
7. **절기 시각**은 lunar-javascript 값이며 독립 천문식(정확도 약 15분)과의 대조에서 최대 13.9분 이내로 일치한다. 한국천문연구원이 발표한 절기 시각표와는 대조하지 못했다 — 절입 시각 몇 분 이내의 출생은 월주·연주가 발표값과 어긋날 수 있다.
8. 접근성은 자동 검사(axe)와 키보드 조작 확인까지다. 스크린 리더로 직접 읽어 보지는 않았다. 사용성(실제 사용자 평가)은 하지 않았다.
9. 해외 출생지는 대표 도시 25곳과 경도 직접 입력이며, 1908년 이전의 표준시 이력은 시간대 데이터가 주는 값을 따른다.
10. **“쉽다”는 자동 검사로 보증되지 않는다.** 자동 검사는 문장 길이·전문용어 표시·되풀이·구조만 본다. 독자 시험(V-22)은 AI 독자 3명이고 채점도 개발자가 했으며, 시험 뒤에 고친 세 가지(삼합·대궁 설명, 사주 대응 접기, ‘N개’ 설명)는 다시 시험하지 않았다. 낱말 자체의 어려움(‘함’, 홍란·고진·과숙, 甲申 같은 간지)은 남아 있다.
11. **분량은 늘었다**(칸 해설 평균 954자 → 1,289자). 사용자 결정(“분량 무관”)에 따른 것이지만, 맨 앞의 “한눈에 보기”만 읽어도 결론을 알 수 있게 한 구조에 기댄 결정이다.
12. ~~교차 보기 2단계(N-05)는 만들지 않았다~~ → **부록 D 로 구현했다**(종합 통변 · 사주 통변 · 통변 비교). 다만 아래 13~21 의 한계가 있다.
13. **통변은 규칙 기반 간이판이고 전문가 감수를 받지 않았다.** 점수표의 수치와 경계(가중치 · 용신 선택 · 격국 판정 등)는 설계자가 정한 값이며 전통 문헌의 정량값이 아니고 통계로 검증하지 않았다. 독립 구현 대조(V-24·V-25)는 “규칙표대로 계산했는가”를 보는 것이지 “규칙표가 명리학적으로 옳은가”가 아니다. 종격·화격·형·해·파·궁간 비화·유년 이하 운은 담지 않았다(설계서 D-10).
14. **두 체계의 판정 일치율은 우연 수준**(일치 33.3% · 보완 42.3% · 엇갈림 24.4% = 서로 무관한 점수의 기대값 33.5 / 42.0 / 24.5%)이다(V-28). 이 간이 규칙으로는 두 방법이 같은 말을 했다는 것이 “맞다”는 증거가 아니며, 통변 비교는 읽을거리와 점검 목록이지 교차 검증이 아니다. 화면에도 그렇게 적었다.
15. **경향 단계는 점수의 상대 위치다.** 예언이 아니고, 한 사람의 구간끼리는 비슷한 단계로 나올 수 있다(T6 은 열 구간이 모두 같은 단계). 사주 점수는 0.1~0.5 단위의 규칙 합이라 단계 비율을 목표와 정확히 맞출 수 없다(사주 대운 최대 5.4%p 어긋남). 경계값은 대한 12구간으로 만들었는데 화면은 100세까지 10구간만 보여, 자미두수 대한 종합 단계는 목표에서 최대 2.6%p 어긋난다.
16. **대한 단계는 지지의 음양에 따라 번갈아 오르내리는 명반이 있다.** 한 대한의 삼방사정이 대한 명궁과 같은 음양의 지지에 놓이고, 본명 칸 점수(삼방사정 합성)의 평균이 지지마다 달라(子午寅申 0.52~0.59 · 辰戌 0.44~0.46 · 丑未 0.31 · 卯酉 0.26 · 巳亥 0.13) 대한 3,600구간의 평균 단계 값이 양 지지 +0.11, 음 지지 −0.18 이다. 규칙의 오류가 아니라 모델의 성질이며, 전문가가 보면 다르게 정할 수 있다(설계서 D-11).
17. **통변 독자 시험**은 AI 독자 3명씩 3차례이고, 입력은 화면에서 접힌 부분과 안내 줄을 뺀 글이며, 채점 규칙과 입력은 개발자가 만들었다. “정리 3.7/5 · 쉬움 3.0/5”는 보통 수준이다. **3차 뒤에 고친 8건은 다시 시험하지 않았다.** 삼방사정 · 별 이름 · 구도 이름 · 간지 이름의 어려움, 세 10년 목록의 되풀이, 맺음 결론 부재는 그대로 남아 있다.
18. **통변 화면의 사람 사용성**(실제 사용자가 결론을 읽고 행동하는지)과 **명리·자미두수 전문가의 문안 감수**는 하지 않았다. 건강·재물·관계에 관한 문장은 생활 점검의 참고이며 진단·투자·법률 조언이 아니다(화면 고지 4줄).
19. **한국식 시각**(I-16)은 사이트 원본이 시계 시각을 그대로 쓰는지 확인하지 못했다. 기본 결과가 사이트와 달라질 수 있다(설계서 C-4).
20. **느린 실행기에서 시간 기준 E2E 검사가 흔들릴 수 있다**(§5·§7). 로컬 실측값은 120~175ms 이지만 CI 에서 한 번 1,269ms 가 나왔다.
21. 사주 대운은 8구간, 자미두수 대한은 100세까지 10구간이라 마지막 두 대한은 짝이 되는 대운이 없다(비교에서 “짝 없음” 15.7%).
